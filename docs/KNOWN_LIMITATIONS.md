# Known Limitations & Operational Disclosures

1. **External Live Credentials Not Provisioned in Local Environment**: Live Razorpay orders/webhooks, SMTP email relay, S3 object storage, and authenticated private GitHub/GitLab/Bitbucket API calls were implemented with real adapters and validated structurally/via signature tests, but require live provider credentials before live production traffic.
2. **Static Analysis vs. Containerized Runtime Execution**: The AI/technical evaluation pipeline performs static AST, pattern, secret, and manifest parsing without executing submitted code. Dynamic runtime test execution inside ephemeral Firecracker/Docker sandboxes is deferred until container orchestration is provisioned.
3. **Marketplace Split Settlements**: Automated multi-party payout splitting requires regulated merchant/escrow onboarding (e.g., Razorpay Route). Currently, when split settlement is disabled, settlements record gross/commission/net splits with manual finance reconciliation (`POST /transactions/:id/confirm-settlement`).
4. **ClamAV / S3 Malware Scanning**: Archive validation enforces magic bytes, Zip Slip traversal rejection, size limits, and zip-bomb ratio ceilings; external ClamAV antivirus daemon scanning should be attached at the object-storage upload pipeline in production.
5. **Local PGlite vs. Multi-Instance PostgreSQL**: Local development uses `@electric-sql/pglite` (single-process PostgreSQL); multi-instance production deployment requires external PostgreSQL (`DATABASE_URL=postgresql://...`) and Redis for distributed rate limiting.
